## 1 范围

本文规定本方案开发全程采用 **BDD（行为驱动开发）** 的工作方式：任何新能力**先写
行为场景（feature），再写实现**；场景文件、步骤实现、被测代码、文档四者同步演进。
本文同时维护全部场景的目录与需求映射。

## 2 规范性引用文件

- docs/01-方案总览.md（需求与决策参数）
- docs/03-需求规格.md（FR/NFR 验收口径）
- docs/04-仓库规划与流程规范.md（提交、变更管理）
- Gherkin 语法（Cucumber 社区规范；本文只用其中文关键字子集）

## 3 术语和定义

| 术语 | 定义 |
|---|---|
| feature 文件 | `features/<能力>.feature`，Gherkin 中文关键字描述的行为场景集 |
| 场景编号 | `SC-M<里程碑>-<两位序号>`，写入 feature 文件 tag 行（如 `@SC-M1-01`） |
| 步骤定义 | `tests/bdd_steps_*.py` 中以 `@given/@when/@then` 注册的 Python 函数 |
| BDD 运行器 | `tests/bdd_runner.py`：解析 feature 文件并逐场景执行步骤定义 |
| 三段式 | 假如（Given 前置态）/ 当（When 动作）/ 那么（Then 可观察结果） |

## 4 BDD 工作流程（每个里程碑固定五步）

1. **场景先行**：在 `features/` 新增/扩展 feature 文件，场景覆盖该里程碑全部验收点；
2. **红灯**：步骤定义先以断言占位，运行确认失败（实现缺失）；
3. **实现**：编写 `tools/<模块>.py` 使场景通过；
4. **绿灯**：`python3 tests/run_tests.py` 全部通过（既有 35 项回归 + 新增场景）；
5. **同步治理**：更新 `manifest.yaml`（planned→delivered）、`AGENT.md` 进度表、
   本文档场景目录表，并按 docs/04 §5 提交（提交说明映射 SC/FR 编号）。

## 5 目录与语法约定

1. feature 文件位于 `features/`，UTF-8，行尾 LF；
2. 关键字采用中文：`功能:`、`场景:`、`假如/假设`、`当`、`那么`、`而且/并且`、`但是`；
3. 每个场景首行 tag 为场景编号（`@SC-M1-01`），步骤文本必须可读、可追溯到验收点；
4. 步骤定义只允许通过注入的夹具（fixture）与被测模块交互，**禁止真实网络调用**；
   真实 GitHub/飞书适配层仅做薄封装，其行为由注入假 fetcher 的场景覆盖；
5. 测试入口不变：`python3 tests/run_tests.py`（BDD 场景随 unittest discover 一并执行）。

> 状态语义：「规划」= 里程碑未开始，feature 尚未编写，测试套件无对应用例（不产生红灯）；
> 「场景先行」= feature 已入库、实现未落（此时测试为红灯，按 docs/06 §5 须立即进入实现）；
> 「已实现」= 全绿。测试入口 `python3 tests/run_tests.py` 不设 skip 机制——
> 不存在「挂在套件里的红灯场景」，红灯只允许存在于实现进行中的工作区。
