## 5 架构概述

系统由五个子系统构成（与目录职责一一对应）：

1. **扫描子系统**（`tools/scan_inventory.py` + `tools/detect_drift.py`）：低频（7 天）增量扫描 + sha 比对漂移检测，产出/维护 `out/inventory.json`，是唯一调 GitHub API 的地方。
2. **计划子系统**（`tools/plan.py` + `ctl` 入口）：读 inventory + `config/policy.yaml`，选块、装箱、输出 `plan.json`；先计划后拉取。
3. **构建子系统**（`docker/*.Dockerfile` + `.github/workflows/build-block.yml`）：L0 工具链镜像（固定 digest）+ 参数化块镜像；产出 `bindings.json`；交付前全层加密，tag = 明文内容 sha256。
4. **融合子系统**（`docker/fused.Dockerfile` + `.github/workflows/verify-fuse.yml`）：拉取解密 → OverlayFS `lowerdir` 挂载 → manifest 软链 → 哈希校验门禁。
5. **治理子系统**（告警 + 缓存 LRU + `plan.json` 审计）：四类告警、1h 节流、缓存预算。

## 6 视点与视图

### 6.1 逻辑视图

核心对象模型：

```
Repo{repo, topics[], labels[], size_est, head_sha, mirror_sha, path_in_manifest, shared_paths[]}
Block{id, match{label|topic}, mode: whole|split-by-repo, oversized_policy, bindings[], expect_max_gb}
Combo{id, blocks[], strategy: runtime-overlay, layout: flat|prefix}
Inventory{repos: Repo[], cursor, last_scanned}          ← 唯一真相源
Plan{bins: [{block_ids[], size_est, est_jobs}], reason} ← 计划存档（审计）
OverlayRule{precedence[], path_rules[{path, pin|isolate}]}
```

关系：`Block.match` 按 label/topic 从 `Inventory` 选择 `Repo` 集合；`Combo` 引用 `Block`；`OverlayRule` 只作用于融合子系统；`Plan` 由 `Inventory + policy` 派生。

### 6.2 数据视图

| 数据制品 | 位置 | 生命周期 | 说明 |
|---|---|---|---|
| `inventory.json` | `out/`（不入库） | 7 天滚动更新 | 字段定义见 DSH-PLAN-001 §7.2 |
| `inventory.csv` | `out/`（不入库） | 随扫描产出 | 人读版 |
| `plan.json` | `out/`（每次存档） | 长期保留（H11 审计） | 记录「当时为什么这么切」 |
| `bindings.json` | 随块镜像产出 | 与镜像同生命周期 | 块 ↔ manifest 条目绑定，diff 限域依据 |
| `config/scan.yaml` | 入库 | 变更走 ADR | 扫描频率/请求上限/预算 |
| `config/policy.yaml` | 入库 | 变更走 ADR | 块/组合/加密/选举规则/告警 |
| 隔离区 `quarantine/` | 运行时 | 人工确认后处置 | 不进入发布镜像 |

关键不变式：
- I1 日常 CI 读写的数据只有 `inventory.json`（零 API）；
- I2 任何阈值/规则必须能在 `config/*.yaml` 找到唯一出处；
- I3 `plan.json` 必须能复现当时装箱决策（输入快照 + 算法版本）。

### 6.3 部署视图

| 运行位置 | 组件 | 资源约束 |
|---|---|---|
| GitHub Actions 定时 job | 扫描子系统（每 7 天、错峰） | `max_requests_per_run=200`，cursor 续跑 |
| GitHub Actions 触发/定时 job | 计划 + 构建子系统 | 单 job 原始体积 ≤ 4.0 GB；缓存 ≤ `cache_gb`（10 GB 平台上限内） |
| GHCR/对象存储 | 加密镜像与 `manifest-index.tar` | 全层加密；tag = 明文内容 sha256 |
| 运行时容器（本地/CI 验收） | 融合子系统 | 解密后 `lowerdir` ≤ 8 层；内核 Overlay 上限 128 |
| 告警通道 | 治理子系统 | github-issue + feishu-webhook，1h 节流 |

### 6.4 过程视图（端到端时序）

```
① scan(7d) ──→ inventory.json ──┐
② drift 检测 ──→ mirror_sha 更新 │
                                ▼
③ ctl plan（读 inventory + policy）──→ plan.json（超预算→切子块/稀疏检出）
④ build-block（固定 digest L0；产出 bindings.json；全层加密；tag=明文内容 sha256）
⑤ 失败→ 告警+plan.json 附件；成功→ verify-fuse：
⑥ 拉取→解密→lowerdir 挂载（≤8 层，左高右低）→ manifest 软链→哈希校验门禁
⑦ 验收：目录可达/体积/校验和 ──→ 通过后可组合使用
```

变更来源矩阵（manifest × mirror）驱动 ③～⑦ 的触发范围，见 DSH-PLAN-001 §12.1。

### 6.5 安全视图

| 关注点 | 措施 |
|---|---|
| 存储保密性 | 交付镜像/制品**全层加密**（age），运行时解密挂载（ADR-007） |
| 密钥管理 | age 私钥、GitHub token 只经环境变量注入；不入库不入日志 |
| API 权限 | fine-grained token，多 token 轮转，受 `max_requests_per_run` 约束 |
| 一致性防线 | manifest 哈希校验失败即阻断；补拉不一致进 `quarantine/`，不进发布镜像 |
| 审计 | `plan.json` 存档 + ADR 变更记录 + 策略唯一出处 |

## 7 关键架构决策（ADR）

| 编号 | 决策 | 理由 | 后果 | 状态 |
|---|---|---|---|---|
| ADR-001 | 按 topic 切片镜像，而非单镜像全量或每仓一镜像 | 单镜像必超 5 GB；每仓一镜像数量爆炸；块级独立可缓存、可组合、可回滚 | 需要融合子系统补足全量查阅体验 | 已确认 |
| ADR-002 | 扫描周期 7 天，inventory 为唯一真相源 | 日常 CI 零 API 消耗；7 天是漂移容忍与配额的平衡（D1） | 漂移最长 7 天后被发现 | 已确认 |
| ADR-003 | 单 job 预算 4.0 GB，k=1.25 | 覆盖估算失真、LFS、加密膨胀（D2） | 超预算块必须切分或稀疏检出 | 已确认 |
| ADR-004 | L0 仅工具链、固定 digest；索引出镜像进运行时卷（选型 B） | 缓存失效沿层传递，索引入镜像会连带全量重建 | 多一次秒级制品下载 | 已确认 |
| ADR-005 | 选举规则：toolchain > self-dev > k8s > edge；`manifest/**` pin toolchain；`**/build.sh` 隔离 | 公共索引唯一权威，自研层次之；确定性裁决（D5） | 被覆盖层同名文件不可见（按设计） | 已确认 |
| ADR-006 | 融合布局混合：self-dev 扁平 / 组合前缀 | 兼顾 `repo sync` 兼容与同名隔离（D4） | 两套布局并存，`policy.yaml` 切换 | 已确认 |
| ADR-007 | **全层加密**（D3，否决「仅最终层加密」） | 需求方对保密性要求优先于增量复用 | ① age 非确定性 → registry 去重失效、层不可差分；② 缓解：tag=明文内容 sha256 保持逻辑身份、绑定 diff 限域重建、cache LRU 预算；③ 运行时先解密再挂载 | 已确认（风险接受） |
| ADR-008 | 合并裁决固定顺序：先 manifest 重建，后漂移补拉，不一致进隔离区 | 「谁后到谁赢」会产生双版本/悄悄覆盖（R16） | 最坏情况人工处置隔离区 | 已确认 |
| ADR-009 | 超大单仓（>预算）：blob:none 浅克隆 + sparse-checkout + mirror 冷备 | k8s 类单仓 2~5 GB「必然超限」（R1） | 镜像内无完整历史，排障走冷备（H8） | 已确认 |
| ADR-010 | 四类告警（超限/扫描失败/漂移/缓存压力），1h 节流，按 kind 聚合 | 防告警风暴（H10）；超限不静默失败（R17） | 通知合并可能延迟个别事件 | 已确认 |
| ADR-011 | **融合验收非特权化**：CI/本地验收用用户态等价校验（`tools/fuse_verify.py` 复用 overlay.py 裁决）替代特权内核挂载验收；内核 OverlayFS 挂载为消费侧运行时语义（运行时 OverlayFS 采用不变） | 2026-11-28 实测 debian:bookworm-slim 与 ubuntu:24.04 仓库均无 overlayfs-tools 包（V2 构建阻断，Issue #4）；特权挂载不可进 CI 门禁 | 内核级挂载行为不在 CI 覆盖，由消费侧部署环境自验 | 已确认（2026-11-28） |

## 8 质量属性与权衡

| 属性 | 目标 | 权衡 |
|---|---|---|
| 配额经济性 | 日常 CI 零 API；周期配额 ≈1 请求/仓库/周期 | 漂移容忍最长 7 天 |
| 构建效率 | manifest 单仓变更 → 仅受影响块重建 | 全层加密使 registry 层级去重失效，靠 diff 限域补偿 |
| 可回滚性 | SHA/内容哈希 tag 永久保留可回指 | registry 存量增长，靠保留策略治理 |
| 可审计性 | 策略唯一出处 + plan.json + ADR | 文档维护成本 |
| 安全性 | 交付边界全加密 | 增量/去重能力换保密性（D3 需求方权衡结果） |
| 兼容性 | self-dev 扁平布局对 `repo sync` 友好 | 组合场景改用前缀，视图路径不同 |

## 9 符合性

1. 本架构描述条款组织遵循 ISO/IEC/IEEE 42010 的「利益相关方—关注点—视点—视图—决策」结构。
2. 每项 ADR 均可追溯到 DSH-PLAN-001 §5 决策参数或 §6/§15 需求与隐患条目。
3. 架构变更 = 重大变更（AGENTS.md §6）：先更新本文档 ADR 与修订历史，再动实现。
